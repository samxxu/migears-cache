## Verdict / 结论

The previous interface-signature P0 was fixed along the way when PHPStan was added (`?int` widened to `null|int|\DateInterval`, consistent across all three declarations). This round found something more troubling: **RedisCache's string reads and writes are asymmetric, which is the precondition for PHP object injection**.

上一轮的接口签名 P0 已在接入 PHPStan 时顺手修好（`?int` 放宽为 `null|int|\DateInterval`，三方一致）。本轮新发现一个更值得警惕的问题：**RedisCache 的字符串值读写不对称，构成 PHP 对象注入的机制条件**。

## P0

### P0-1

- **Status / 状态**: Open
- **Where / 位置**: `src/RedisCache.php:233-236,238-242`
- **Verification / 验证**: mechanism reproduced (`unserialize` returned a stdClass), RedisCache itself unverified because the default suite excludes the integration group
- **EN**: RedisCache writes strings raw and everything else serialised (`is_string($value) ? $value : serialize`), but on read it runs `@unserialize()` over **any** string without passing `allowed_classes`. A stored string like `'O:8:"stdClass":0:{}'` therefore comes back as an object rather than a string, and if that string came from user input it is an object-injection primitive. `getMultiple` and `getOrSet` share the path
- **中文**: RedisCache 写入时字符串原样存、其余序列化（`is_string($value) ? $value : serialize`），读取时对**任意字符串**执行 `@unserialize()` 且未传 `allowed_classes`。后果：存入形如 `'O:8:"stdClass":0:{}'` 的字符串，读出来是对象而非字符串；若该字符串来自用户输入，即构成对象注入。`getMultiple` 与 `getOrSet` 同路径

## P2

### P2-1

- **Status / 状态**: Open

- **Verification / 验证**: —
- **EN**: `RedisCache::set()` passes `ttl <= 0` straight to `setex` (which fails or errors), while PSR-16 requires deleting the entry in that case[1]; ArrayCache behaves correctly (`ttl <= 0` means already expired), so the two implementations diverge while the README claims full PSR-16 compatibility
